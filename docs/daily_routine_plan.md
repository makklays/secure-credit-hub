# Техническое задание и пошаговый план доработки системы микросервисов (Java WebFlux)

Этот план разработан для систематической доработки, тестирования и оптимизации вашей микросервисной архитектуры на базе Reactive Spring (WebFlux).

---

## Часть 1: Единый стандарт доработки для каждого микросервиса
Применяйте эти 5 шагов последовательно к **каждому** из 7 микросервисов.

### 1. Ревизия кода и архитектуры (Архитектурный аудит)
* **Анализ реактивности**: Убедитесь, что нигде не используются блокирующие вызовы (`block()`, `blockFirst()`, `Thread.sleep()`).
* **Пул потоков**: При интеграции с блокирующими драйверами (например, если используется старый JDBC/сервисы) выносите их на `Schedulers.boundedElastic()`.
* **Валидация**: Добавьте `@Valid` и `jakarta.validation` на уровне DTO для входящих запросов.
* **Обработка ошибок**: Реализуйте глобальный обработчик исключений через `@ControllerAdvice` или `ErrorAttributes`, возвращающий понятные реактивные ответы (`Mono.error`).

### 2. Финализация URL API и Документация (OpenAPI/Swagger)
* **Проверка эндпоинтов**: Приведите REST URL к единому стандарту (существительные во множественном числе, например: `/api/v1/cards/{id}`).
* **Интеграция Swagger**: Подключите зависимость `springdoc-openapi-starter-webflux-ui`.
* **Аннотирование**: Добавьте `@Operation` и `@ApiResponse` для каждого эндпоинта.
* **Экспорт контрактов**: Сгенерируйте и сохраните схемы `openapi.yaml` для настройки API Gateway.

### 3. Функциональное и Реактивное тестирование (Тесты)
* **Unit-тестирование**: Покройте бизнес-логику (сервисы) с помощью `StepVerifier` из библиотеки `reactor-test`.
* **Слайс-тестирование контроллеров**: Используйте `@WebFluxTest` совместно с реактивным `WebTestClient`.
* **Интеграционные тесты**: Настройте Testcontainers для баз данных (R2DBC) и используйте `WireMock` для симуляции ответов соседних микросервисов.

### 4. Нагрузочное тестирование эндпоинтов
* **Инструмент**: Используйте **Gatling** (идеален для WebFlux, так как сам написан на Netty) или **Apache JMeter**.
* **Сценарии (Scenarios)**: Напишите изолированные скрипты для каждого эндпоинта (проверка GET, POST, PUT, DELETE).
* **Профили нагрузки**:
  * *Тест стабильности (Smoke)*: 5–10 rps (проверка корректности под нагрузкой).
  * *Стресс-тест (Stress)*: Постепенное повышение до отказа системы (поиск точки излома).
  * *Тест выносливости (Soak)*: Средняя нагрузка в течение 2–4 часов (поиск утечек памяти/пулов).

### 5. Контейнеризация и Логирование
* **Dockerfile**: Создайте многоэтапные (multi-stage) Docker-файлы на основе Eclipse Temurin (JRE).
* **Конфигурация**: Вынесите параметры в `application.yaml` с возможностью переопределения через Docker environment variables.
* **Логирование**: Настройте структурированный JSON-лог через Logback для удобного сбора в систему мониторинга.

## Часть 2: Пошаговый план работы по микросервисам

### Шаг 1: Микросервис пользователей и авторизации (Auth Service)
*Базовый фундамент безопасности всего проекта.*
* **Доработка**: Реализация JWT (генерация, валидация, обновление через Refresh Token). Реактивный `ReactiveAuthenticationManager`.
* **Критические URL**: `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `GET /api/v1/users/me`.
* **Специфика тестов**: Изолированные тесты шифрования паролей (BCrypt) и валидации просроченных токенов.
* **Нагрузка**: Эндпоинт `/login` требует проверки на производительность криптографии (хэширование паролей сильно нагружает CPU).

### Шаг 2: Микросервис валют (Currency Service)
*Справочный высокопроизводительный сервис.*
* **Доработка**: Интеграция с внешним API курсов валют (через реактивный `WebClient`), кэширование курсов в Redis (реактивный `ReactiveRedisTemplate`).
* **Критические URL**: `GET /api/v1/currencies`, `GET /api/v1/currencies/convert?from=USD&to=EUR&amount=100`.
* **Специфика тестов**: Мокание ответов внешних банковских API с помощью `WireMock`.
* **Нагрузка**: Тестирование кэша. Убедиться, что при 1000+ rps сервис не падает из-за лимитов внешнего API.

### Шаг 3: Микросервис кредитных карт (Card Service)
*Компонент хранения конфиденциальных данных.*
* **Доработка**: Реактивный доступ к БД через R2DBC (PostgreSQL/MySQL). Валидация алгоритма Луна для номеров карт. Маскирование номеров в логах.
* **Критические URL**: `POST /api/v1/cards`, `GET /api/v1/cards/user/{userId}`, `PATCH /api/v1/cards/{id}/block`.
* **Специфика тестов**: Использование `StepVerifier` для проверки реактивных транзакций (выпуск карты + привязка к счету).

### Шаг 4: Микросервис оплат (Payments Service)
*Бизнес-критичный сервис с высокими требованиями к транзакционности.*
* **Доработка**: Обработка транзакций, интеграция с платежными шлюзами. Важно реализовать паттерн Идемпотентности (обработка дубликатов запросов).
* **Критические URL**: `POST /api/v1/payments/charge`, `GET /api/v1/payments/history/{cardId}`.
* **Специфика тестов**: Имитация отказов сети и долгих ответов платежного шлюза. Проверка отката транзакций.
* **Нагрузка**: Стресс-тестирование эндпоинта `/charge` с одинаковыми `Idempotency-Key` токенами.

### Шаг 5: Микросервис агрегатор (Aggregator Service)
*Оркестратор реактивных потоков.*
* **Доработка**: Параллельные неблокирующие вызовы к Card Service, Currency Service и Payments Service с помощью `Mono.zip()` или `Flux.merge()`. Компоновка единого DTO для фронтенда.
* **Критические URL**: `GET /api/v1/dashboard/summary/{userId}` (собирает профиль, карты, балансы и последние оплаты).
* **Специфика тестов**: Комплексные интеграционные тесты. Проверка поведения агрегатора, если один из зависимых микросервисов отвечает ошибкой или таймаутом (`.timeout()`, `.onErrorResume()`).
* **Нагрузка**: Важнейшая точка нагрузочного тестирования. Проверка утечек памяти при сборке больших объектов в реактивных потоках.

### Шаг 6: Микросервис Gateway API (Spring Cloud Gateway)
*Единая точка входа системы.*
* **Доработка**: Настройка `RouteLocator`. Интеграция с Auth Service (глобальный фильтр `GatewayFilter` для валидации JWT и проброса `X-User-Id` заголовков вглубь системы). Настройка Rate Limiting (ограничение частоты запросов через Redis).
* **Критические URL**: Маршрутизация всех вышеописанных URL. Внутренний эндпоинт `/actuator/health`.
* **Специфика тестов**: Проверка прохождения запроса с валидным JWT и блокировки с невалидным (401 Unauthorized).
* **Нагрузка**: Сквозной нагрузочный тест через Gateway ко всем микросервисам. Gateway должен держать кратно больше нагрузки, чем внутренние сервисы.

### Шаг 7: Микросервис мониторинга (Monitoring Service)
*Наблюдаемость всей инфраструктуры.*
* **Доработка**: Сбор метрик (Prometheus + Micrometer) со всех микросервисов. Настройка дашбордов Grafana. Подключение Spring Boot Admin для визуализации состояния реактивных потоков и пулов Netty.
* **Критические URL**: Сбор данных с эндпоинтов `/actuator/metrics` и `/actuator/prometheus` на каждом сервисе.
* **Специфика тестов**: Проверка корректности отправки кастомных бизнес-метрики (например, счетчик успешных платежей).
* **Нагрузка**: Проверить, что сам процесс сбора метрик не деградирует производительность основных сервисов при высокой нагрузке.

## Часть 3: Пошаговый сквозной план запуска и тестирования всей системы

```
[Шаг 1-7: Локальная доработка и тесты] 
                  │
                  ▼
[Шаг 8: Развертывание локального окружения (Docker Compose)]
                  │
                  ▼
[Шаг 9: Сквозное функциональное тестирование (Postman)]
                  │
                  ▼
[Шаг 10: Комплексное нагрузочное тестирование (Gatling/JMeter)]
```

### Шаг 8: Создание единого окружения (`docker-compose.yml`)
1. Поднимите инфраструктурные контейнеры: **PostgreSQL/Р2DBC**, **Redis**, **Prometheus**, **Grafana**.
2. Упакуйте все микросервисы в образы и добавьте их в общую сеть docker-compose.
3. Убедитесь, что настроены `healthcheck` (сервисы должны запускаться строго после готовности баз данных).

### Шаг 9: Сквозное ручное/автоматическое тестирование API
1. Создайте коллекцию в **Postman** или **Insomnia**.
2. Пропишите переменные окружения (base_url = Gateway API).
3. Создайте сквозной сценарий (End-to-End):
   * Регистрация и логин пользователя -> Получение токена.
   * Создание кредитной карты с авторизационным токеном.
   * Запрос данных через Агрегатор (проверка структуры ответа).
   * Проведение платежа -> Проверка списания баланса.

### Шаг 10: Финальное нагрузочное тестирование всей системы
1. Запустите мониторинг (Grafana) для отслеживания CPU, Memory (памяти JVM) и активных потоков Netty.
2. Запустите разработанные скрипты нагрузочного тестирования через **Gateway API**.
3. **Целевые метрики для WebFlux**:
   * *Время ответа (Latency)*: p95 < 100мс, p99 < 300мс.
   * *Пропускная способность*: отсутствие ошибок 5xx при пиковых нагрузках.
   * *Память*: стабильный график Garbage Collection (без эффекта "пилы" с постоянным ростом, что указывает на Memory Leak).
